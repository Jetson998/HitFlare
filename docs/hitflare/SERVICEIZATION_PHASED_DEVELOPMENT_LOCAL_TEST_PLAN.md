## 1. 复审结论

采用单一 AI 总开发端到端推进的串行流程。AI 在每阶段负责后端、权限 UI、业务前端、文档、本地测试和证据；用户在阶段出口人工审查并决定是否验收。服务端接口完成后，业务前端仍可能把浏览器本地 store 当成权威来源，因此每个业务域都必须以“后端存储、前端切换、权限交互、本地故障测试”共同通过作为阶段出口，不能按代码层或前后端拆开验收。

复审开始时的 v0.18.3 基线提供以下底座；服务化实施后的实际状态以各阶段验收包为准：

- `server/auth.mjs` 已有用户、角色、状态和 HttpOnly session；需要扩展默认租户、统一 `AuthContext`、能力快照、审计和生命周期处理，不重新开发一套账号系统。
- Agent 和反推已经有各自的 SQLite、任务状态、SSE、幂等和假模型测试。反推是独立的新业务功能，已经服务端化的反推任务不能被写成“原有资产/历史/媒体/画布已完成服务化”。
- `server/index.mjs` 的 `createApp` 可注入临时 `dataDir`、Agent 假模型和反推假模型，适合建立不触碰真实数据的 HTTP、重启和失败测试。
- 图片、视频、资产和画布工作台仍主要使用浏览器的 localforage；`use-config-store` 还会持久化明文 API Key，`app-sync` 和配置导出还存在旧 WebDAV/秘密导出路径。这些必须在对应阶段收口。
- 当前 Node 任务是单进程内存任务。首轮保留“重启标记 interrupted、没有自动重复付费请求”的行为，不把队列、多实例和自动续跑隐含加入服务化范围。

服务化完成的判定是“登录账号下的服务端数据闭环”，不是页面能打开，也不是 `/api/health` 返回 200。反推现有测试通过或反推页面可用，只能证明反推自身的新增功能及其回归边界，不能抵扣原有业务域的阶段工作量。

## 2. 总开发责任和架构范围

由一个 AI 总开发负责端到端交付后端、权限前端、业务前端、本地验证和阶段证据。按阶段串行工作；每阶段完成后提交可审查的具体结果并暂停，默认用户人工验收通过后才继续。用户明确授权延后验收并启动后续阶段时，保留前序待验收状态，按新授权推进；验收发现的问题仍需修复并重新提交。

| 范围 | 本计划中的责任 |
| --- | --- |
| 身份、租户、session、用户管理、最终 API 鉴权 | AI 总开发实现后端权威上下文、鉴权和前端入口/交互，并验证两端合同 |
| 权限 UI | AI 总开发完成菜单、路由、按钮、401/403、账号切换清理和生命周期；不以 UI 隐藏代替后端拒绝 |
| 渠道、偏好、密钥 | AI 总开发完成服务端归属/密文和配置页面、模型选择、渠道测试、执行调用接入 |
| 资产、媒体、生成历史、画布 | AI 总开发完成后端接口和权限校验、前端数据源切换及现有交互 |
| Agent、反推 | AI 总开发保留各自业务格式和任务状态，接入统一身份、渠道凭据、撤权、日志和回归，不重写成一个大网关 |
| 灵感来源、管理/调用用量/错误日志、存储运维 | AI 总开发完成日志记录、管理员查询投影、筛选后台、权限控制和本地验收 |
| 旧浏览器数据、WebDAV、备份恢复、迁移 | AI 总开发按本计划交付保护与已确认范围；需要新增产品能力的部分作为条件工作包，不默认扩大主线 |

首轮架构继续使用一个 Node/systemd 服务，当前实现由 auth、Agent、反推、workspace、generations、canvases 六个 SQLite 库组成。工作台库保存渠道、偏好、密文凭据、资产与媒体索引及调用元数据；生成库保存任务/调用/输出/操作，画布库保存整文档/revision/附件/幂等收据，媒体字节保存为文件对象。账号变更审计与变更写入同一个 auth 库事务，P5 提供统一管理投影。跨库的“保存为资产”使用幂等流程，不声称跨 SQLite 天然原子；P5 备份恢复需协调六库和媒体对象。每一条新业务记录都由 session 派生 `tenant_id` 和 `owner_user_id`，不能接受请求体或请求头中的归属字段作为事实。

模型执行首轮保持混合模式：Agent/反推提交 `channelId + model + 业务输入`，服务端校验归属并在内存中解密使用；浏览器直连的图片/视频暂时使用仅本人可读的 runtime-secret，不持久化明文、不写日志、不放入导出。模型列表、渠道测试和所有隐含读取 Key 的路径都必须一起覆盖。全部模型迁移到服务端、多实例队列和重启续跑另行评估。

## 3. 本轮反馈后的决策与待定边界

以下是用户对方案的明确反馈和总开发据此收敛的首版方案；用户已明确授权启动开发，按阶段门实施。继续保留混合模型执行和仅本人 runtime-secret。默认单租户、固定 `admin|user` 角色、session 派生归属、未就绪不返回假空列表等合同保持不变。

### 3.1 管理员代设密码与日志后台：已确认

用户确认管理员可以帮助目标用户设置密码，管理员具有较大的管理权限。沿用既有代设/重置流程，不新增邮箱恢复或“管理员无法使用已知重置密码登录”的前置要求；重置撤销目标用户全部旧 session/事件流。审计记录操作者、目标用户、动作、时间、结果、requestId 和安全错误码，禁止记录新密码、旧密码或密码 hash。用户可使用既有本人修改密码功能。

应用管理角色可以查看全站操作、调用/用量和错误元数据。代设密码不自动扩大为管理员直接浏览他人资产、画布、提示词全文和 API Key 的权限；如将来开放这类能力，单独定义入口和审计。本文不承诺防止持有用户重置密码的管理员以该用户身份登录。

日志后台参考 New API 的查找/筛选体验，按三类组织，可按时间、用户、渠道、模型、业务类型、状态、请求 ID 查询并进入脱敏详情；日志查询接口统一管理员鉴权：

| 类别 | 应记录的内容 | 记录与展示规则 |
| --- | --- | --- |
| 管理操作 | 建号、禁用/启用、改角色、重置密码、来源维护、备份/恢复、存储清理；操作者、目标、结果和关联 requestId | 账号变更与审计同事务；其他管理动作有开始/完成/失败记录，不含秘密和内容 |
| 调用/用量（消费操作） | 用户、taskId、callId、调用阶段、渠道 host、模型、执行位置、状态、耗时、输出数量、供应商返回的 token/usage 或费用 | 一个任务可有多次实际调用；一次调用也可返回多张图；真实返回、客户端报告与估算分开；未返回字段为 null/“未返回”，不是 0，不凭输出数量推算金额 |
| 错误 | 所属业务/阶段、taskId/callId、HitFlare 错误码及 HTTP 状态、上游 HTTP 状态与原始 code/type、脱敏信息、供应商 request ID、发生时间和受理情况 | 包含鉴权、模型、上传、保存、迁移和备份失败；400/403 等上游码值必须保留，不只存中文描述；同一调用的异常不重复计作消费 |

供应商未返回金额时，本轮不新增平台计费或价格换算引擎。浏览器直连记 `client_reported`，服务端执行记 `server_observed`；usage/金额还需标明实际字段来源，不能把“服务器收到了客户端报告”当成供应商账单。Key、Cookie、Authorization Header、完整提示词、媒体字节和带秘密的 URL 都不进入日志。应用管理员日志与部署运维原始日志用途分开，原始异常也需要脱敏。

#### 3.1.1 上游错误码与任务/模型调用/输出关联：已确认

用户明确要求：大模型返回的 400、403 等码值是排障依据，必须记录；一个任务生成多张图时，必须能追踪其下的多次模型调用。采用以下关联合同，不用一条任务状态覆盖全部调用明细：

```text
业务任务 taskType + taskId
  ├─ 模型调用 callId：阶段/图片槽位/尝试序号、渠道、模型、结果、错误、usage
  │    └─ 输出 outputId + outputIndex：关联生产该输出的 callId
  └─ 其他模型调用 callId：各自保留成功、失败、取消或结果未知的事实
```

- 图片/视频工作台以 `generationId` 作为业务 `taskId`；Agent 和反推保留原任务 ID，以 `taskType + taskId` 区分业务，不为日志重建一套全文任务。工作台 Agent 发出的任务 ID 如存在，只作为关联来源，不冒充供应商 request ID。
- 在实际模型请求适配器处生成 `callId`，每次真实发起的生成/推理请求独立记录。任务在参数或权限校验阶段被拒绝，可以没有模型调用；调用记录先创建但尚未发送，也不能计为已执行调用。服务端执行在发送前持久化调用身份；重启或发送确认丢失时保留不确定状态，不补造供应商已接收的结论。
- 当前 `/image` 将批量数量展开为多个 slot，并传 `count=1`；因此通常一次批量任务对应多次模型请求。通用 OpenAI 生成/编辑接口仍可单次 POST 带 `n` 返回多张图，Gemini 适配器则按 count 展开请求。保持既有执行行为：按实际请求计数，一次请求返回多张图时使用同一个 `callId` 和多个 `outputId`，不能凭图片数量伪造多次调用。自定义脚本只可记录受控请求入口实际观测到的调用，无法观测的内部请求不能伪造或估算为已确认调用。
- 同一任务内的手动图片重试保留槽位关联，新增 `callId`、`attemptNo` 和 `retryOfCallId`，旧失败记录保留。反推沿用“重试新建任务并关联旧任务”的合同，另记 `retryOfTaskId`；observe/refine 是两个阶段调用，不是重试。幂等重放、重复日志上报、快照恢复和应用 SSE 重连不新增模型调用。
- 模型调用的输出与保存状态分开：调用成功但媒体上传失败，仍保留调用成功与实际 usage，另记保存错误。部分图片成功、部分失败时，任务汇总显示各项结果；不能把整批只写成单一失败，也不能隐藏某个失败调用的 403。
- 视频创建任务的模型请求按一次调用记录；后续轮询、媒体下载和上传的 HTTP 请求作为操作记录关联该调用，不计作新的生成调用。模型列表/渠道测试也记录请求错误和状态，但与生成调用/消费统计分开。

调用与错误 DTO 至少保留以下结构化字段；字段命名在 P1 冻结，错误信息在转为 UI 文案之前提取：

| 字段 | 含义和要求 |
| --- | --- |
| `taskType`、`taskId`、`callId`、`requestId` | 业务归属、实际模型调用身份、HitFlare 接口/操作请求身份分别记录；三者不能混用 |
| `stage`、`slotIndex`、`attemptNo`、`retryOfCallId` | 区分多图槽位、Agent/反推阶段及同一逻辑操作的尝试；无槽位时为 null |
| `channelId`、`baseUrlHost`、`model`、`executionMode`、`reportSource` | 每次调用自己的渠道/模型及来源；浏览器报告不能自行指定 `server_observed` |
| `status`、`dispatchedAt`、`finishedAt`、`durationMs` | 区分未发送、成功、失败、取消、中断与结果未知；不从超时或取消推断未计费 |
| `appHttpStatus`、`appErrorCode`、`errorOrigin`、`failureStage` | HitFlare 自身的响应/错误及发生环节；后台异步执行没有对应应用响应时状态可为空 |
| `upstreamHttpStatus` | 实际观察到的上游 HTTP 状态，保留 400/401/403/404/408/413/422/429/5xx 等具体值；没有收到响应时为 null，不虚构 500 或 504 |
| `upstreamErrorCode`、`upstreamErrorType`、`upstreamFinishReason`、`upstreamRequestId`、`providerTaskId` | 从供应商已知错误字段、完成/拒绝原因、白名单响应头或 SDK 提取；安全原始 code 区分数值与字符串，未返回为 null，不用 HitFlare 码覆盖 |
| `errorMessageSafe`、`producedOutputCount`、`usage`、`usageSource`、金额与币种来源 | 脱敏说明、实际输出与用量；只存已定义的安全字段，不存供应商原始正文，未返回不当作 0 |

错误记录规则：上游 HTTP 403 可以同时对应 `appErrorCode=PROVIDER_HTTP_ERROR` 和 `upstreamErrorCode=permission_denied`；应用接口是否返回其他状态按既有合同处理，不能丢失上游 403。HTTP 200 的流内错误/拒绝也要记录供应商 code/type 或完成原因，不改写成上游 HTTP 500。非 JSON/HTML 错误仍保留观察到的状态码，只给安全概括；浏览器 CORS/断网无法读取响应时标明传输错误和未知上游状态。代理返回的码要注明来源，不能推断为最终模型返回的码。错误字段仅提取安全标量，遇到密钥、提示词或 URL 等敏感内容仍脱敏，不整段复制正文或 headers。

统计分别展示 **任务数、实际模型调用次数、调用成功/失败/未知数、生成输出数、成功保存输出数**。usage/金额按 `callId` 去重汇总；一条调用返回多张图时，用量只汇总一次，不擅自均摊为每图真实消费。例如一个任务请求 3 张图，首轮 3 次调用中一条返回 403，用户仅重试该槽位且成功：保留 1 个任务、4 次调用、1 条失败调用和 3 张最终输出。管理员可由任务展开各调用，再按上游 HTTP 状态、上游 code/type、渠道、模型和供应商 request ID 查错；仅展示输出 ID、数量等元数据。

### 3.2 WebDAV：总开发决定首轮停用旧同步

当前 WebDAV 是浏览器把本机的资产、画布、图片/视频日志打包到远端存储，再下载合并回本机。它服务于浏览器数据同步，不是新服务器数据库的备份方式，也不能自动识别这批旧数据属于哪个账号。

首轮按以下方案交付：P2 配置切换时关闭旧 WebDAV 同步入口、自动调度和合并回写；保留旧配置/远端文件，不擅自删除。账号的数据同步统一由新服务器接口完成；P5 服务器备份通过部署侧工具统一备份身份、Agent、反推、workspace、generations、canvases 六个库和媒体对象，并在隔离目录演练恢复，恢复时暂停写入、校验 schema/清单/checksum、保留恢复前备份和管理日志。首轮不开 WebDAV 内容下载或恢复 Web UI。

后续确需远端 WebDAV 备份，再让服务器上传经过标准工具加密的备份归档；密钥与归档分开保管，恢复经过一致性与版本校验，不复用旧的浏览器业务合并代码。这是后续工作包，不影响首版账号数据服务化。

### 3.3 上传大小与 413 气泡提示：已确认

按本轮“可以”的反馈，确认前序上传建议：**图片 25 MiB、音频 100 MiB、视频 500 MiB，每个文件分别计量**。`1 MiB = 1024 × 1024 bytes`；适用于新通用媒体以及服务化接入后的用户参考图/输出保存。既有供应商或专用格式有更严格要求时，由该调用环节另行提示，不能用服务器保存上限代替供应商限制。

前端文件选择后先检查已知大小；后端仍以实际接收字节为准，采用成熟 multipart 流式解析写临时文件，超限返回 `413 + FILE_TOO_LARGE`，响应提供文件类型和 `maxBytes`，不生成可读对象索引。反向代理总请求体限制应留出 multipart 元数据空间并与应用合同一致，避免代理提前返回无法辨认的 HTML 错误。

气泡使用项目现有 Ant Design message，由一次用户操作的统一错误入口展示，例如“图片超过 25 MiB 上限，请压缩后重新上传”。预检拒绝和服务端 413 都有提示；即使代理只返回 413，也能显示明确文案。保留本次选择/输入，不跳转、不自动重试；组件和请求层不能各弹一次。同批失败汇总提示并逐项标失败，已上传成功的对象不重复上传。生成已经成功但结果上传超限时提示“生成完成，保存失败”，保留尚在内存的结果供用户下载/处理，不重复调用模型。

### 3.4 并发、重试、轮询：已确认复用优先，单一策略

本轮确认“已有沿用，缺失补充，不多处叠加”。P1 建立策略清单，按真实执行边界记录控制者、超时、重试次数、并发来源和取消行为；P2/P3 按此接入。页面防连点、供应商批量数量 `n`、真实 HTTP 并发和持续 GET 轮询是不同概念，不能互相冒充限制。

| 当前机制（源码核对） | 首轮处理 |
| --- | --- |
| Agent `maxRetries: 0`、180 秒、手动 retry 和 requestId 幂等 | 沿用；外层不再套自动重试，不因保存失败重发付费调用 |
| 反推手动 retry、新任务关联旧任务、requestId/inputHash 去重、显式 stop | 沿用；两阶段模型调用不是失败重试；页面断线恢复快照不创建新任务 |
| 图片页 `generationLockRef`、批量 slot 的 `Promise.allSettled`；部分供应商适配器还有 `Promise.all` | 保留防连点/批量语义；若需补真实请求调度，在最接近实际调用处控制，各层不再重复展开同一批任务或加同一 limiter |
| 视频页、通用视频服务、插件各有轮询路径 | 每条调用路径只由一个现有轮询器负责，不另包第二个轮询器；查询失败/耗尽等待不自动重发创建任务 POST |
| 旧 WebDAV `FILE_CONCURRENCY = 3` | 随旧同步停用；它不是新媒体服务器上传上限，不能与新策略叠加 |
| 尚无新通用媒体上传的统一并发/失败策略 | 用户补充确认仅沿用现有机制，暂不新增上传并发或超时限制；媒体 service 统一上传/取消和大小校验，失败手动重传，不自动重试 |

付费 POST 继续关闭自动重试；手动重新生成与幂等重复提交分开记录。GET 查询、结果上传、对象绑定等缺失策略可以补充，但只有确认重试次数/间隔并保证幂等后才启用，SDK、HTTP 客户端和业务层只能有一个自动重试责任者。上传失败可以重试保存已获得的字节，不能转成再次生成；401/403/413 和取消不自动重试。

用户已确认“只沿用现有机制，暂不新增并发和超时限制”；撤销前序媒体并发每用户 2、进程 4 和无进展超时 120 秒的建议。本轮沿用已存在的模型超时，不静默新增外层超时或上传调度限制。

### 3.5 清理策略：先说明和验证，物理删除规则未确认

清理主要解决服务器磁盘上的无用文件，不清空正常资产或用户历史。例如一张图片同时被“我的资产”、生成历史和画布使用：

1. 用户删除资产后，资产从列表隐藏并移除其引用；文件不立刻物理删除。
2. 历史或画布仍引用该图片时，预览/下载继续正常，扫描不能把它判作孤立对象。
3. 最后一个引用也移除后，文件才成为“待清理对象”；后台显示候选数量和可释放空间，不直接删文件。
4. 管理员查看扫描结果并显式执行清理时，服务器再次检查引用，避免扫描后新引用产生的竞态；记录操作者、对象数、释放字节和结果。

上传中断留下的临时文件、存在文件但无索引的对象、索引指向缺失文件需要分别处理；缺失文件不能靠删除业务记录掩盖问题。跨用户 checksum 相同不合并归属，清理 A 的对象不能影响 B。清理不包含旧浏览器数据、备份和审计日志，它们各有独立保留规则。

首版先实现只读扫描和本地测试，自动物理删除保持关闭。前序“每日扫描、无引用满 30 天后可手动删除”是供用户理解的建议，尚未确认；扫描周期、宽限期和是否开放恢复入口不作为已定默认值。本地验证覆盖共享引用、最后引用移除、扫描后重新引用、半成品、缺失文件、跨账号和重复清理；破坏性测试只使用合成数据。

### 3.6 剩余待决定项

未归属旧浏览器数据暂时封存，不自动读取、认领或清空；主动导入/明确清空仍待产品选择。日志保留周期、配额、分页、其他格式白名单、新上传并发/超时数值以及清理周期/宽限期，在对应阶段前按“环节、现有值、建议值、失败行为、确认状态”冻结。已确认的密码代设、WebDAV 首版范围、上传大小和 413 体验不重复申请确认。

## 5. 分阶段开发和本地化测试

每个阶段都按同一顺序推进：

1. **AI 完成本阶段全栈实现**：按阶段范围完成接口、数据、权限 UI 和业务页面；不跨阶段实现未冻结的后续范围。
2. **AI 完成本地确定性验证**：使用临时数据根目录、三个账号和假模型，不访问生产。
3. **AI 完成独立浏览器验证**：使用新的浏览器上下文或测试页面，不关闭用户现有窗口；桌面优先 1440×900 或 1920×1080，窄屏作为补充。
4. **AI 完成持久化、重启和失败验证**：检查 schema、状态、文件和晚到结果；故障测试检查恢复结果和半成品。
5. **AI 提交阶段验收包并暂停**：列明变更文件/行为、测试命令和实际结果、截图或其他证据、P0/P1、`not_run`、风险及恢复办法。用户人工对照本阶段出口验收；未明确通过前不开始下一阶段，未通过则只修当前阶段并重交。

人工验收是阶段放行门，不由 AI 自行代签。验收通过只允许启动计划中的下一阶段，不等于线上部署或生产发布授权。

每次验收包同时提供本地访问入口、测试账号使用办法（密码不放公开证据）、可直接照做的人工操作步骤和预期结果，以及 AI 已执行/未执行的测试清单。用户无需自行补齐前后端联调或自动化测试；人工重点判断业务是否符合预期，并抽查关键隔离、失败和恢复行为。P1 以合同和恢复证据审查为主，后续阶段增加已交付页面的实际操作。阶段状态依次记为“待开发 → AI 开发/自测 → 待人工验收 → 人工通过”；未通过则记问题并回到当前阶段修复。“收到”“理解”不作为验收通过记录。

每个阶段的验收包固定包含：

1. 本阶段目标、范围和明确不包含的内容；
2. 变更文件与用户可见行为；
3. 本地启动命令、临时数据目录、测试账号角色和人工操作步骤；
4. AI 已执行的 API、权限、失败、重启和浏览器检查，以及每项 `passed/failed/not_run`；

6. 已知问题、风险、回滚方式和下一阶段依赖。

验收包末尾明确写出“请人工验收 Px：通过 / 不通过；如不通过请列出用例编号和现象”。AI 不把用户的查看、回复或“理解”当作通过。

阶段门针对该阶段已交付范围。未服务化模块只能在隔离本地候选中保留原能力，不能把部分完成的版本声明为全应用多用户隔离通过。模块切换后，401/403、网络失败和 `SERVICE_NOT_READY` 都不能回退读取旧共享 store；未归属旧数据保持封存，不能用服务端空列表覆盖。权限菜单隐藏检查贯穿各阶段，总体隔离结论到 P5 才给出。

### P4：画布与引用（附件、revision 和删除恢复保护）

执行节奏：用户已明确将 P3 人工验收延后并授权 P4；P4 已完成 AI 开发、本地自测和 [验收包](./SERVICEIZATION_P4_ACCEPTANCE.md)。P2/P3/P4 保留待集中人工验收状态，用户已明确授权启动 P5。

**开发步骤**

1. 实现画布项目列表、整文档读写、重命名、删除 tombstone、附件关系和 `revision` 乐观并发控制；文档不得持久化只能当前浏览器使用的 `blob:` URL 或 IndexedDB key。
2. 画布保存前验证所有媒体/资产引用属于当前用户；删除和清理流程检查历史、资产和画布引用，不从旧同步或缓存复活删除项。
3. 将 `use-canvas-store` 的服务端数据源、400ms 延迟保存、账号 epoch 和 late-response guard 接入；将 chatSessions 等现有整文档字段按冻结 schema 保存，避免无关拆表。
4. 验证 P2 已关闭的旧 WebDAV 合并链路不会回写服务化画布；新备份恢复如被选择交付，也必须经过版本、归属和审计流程。

**本地测试步骤**

- `CANVAS-001~010`：创建、保存、跨设备打开、列表隔离、附件归属、删除、无 blob URL、猜 ID。
- `CANVAS-008`：两个标签页加载同一 revision；A 保存后 B 用旧 revision 保存必须 409，不能静默覆盖。
- `CANVAS-CONFLICT-001`：409 后保留当前账号内存草稿和冲突提示，让用户选择重载服务器版本或另存项目；不自动覆盖/合并。401/403 后清理可见状态，待本人重新登录再决定恢复，不能给下一个账号展示草稿。
- 延迟保存注入：账号切换、关闭页面、网络失败和重连期间的旧保存不得写入新账号；删除后的晚到保存不能复活项目或附件。
- 失败注入：文档 JSON 无效、附件不存在、数据库提交失败、媒体引用被删除，均返回明确错误并保留上一个有效 revision。
- 浏览器：打开/保存/重命名/删除、资产拖入、附件预览、刷新、双标签冲突、admin/bill/alice 切换；桌面 1440×900/1920×1080 检查画布占用和权限入口。
- 重启：同一临时数据根目录重启后文档和附件仍可打开；旧本地缓存、WebDAV 或 Blob URL 不得恢复已删除内容。

**AI 阶段出口**：画布换设备可用，旧 revision 不能覆盖，附件和删除关系可验证；不会因账号切换或晚到保存把 A 的项目写入 B。**人工验收重点**：保存/冲突/删除/刷新流程、账号切换后无旧数据闪现、WebDAV 不复活已删除项目。用户已明确延后 P4 人工验收并授权启动 P5，P4 保留待验收状态。
